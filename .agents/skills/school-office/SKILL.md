# school-office — 학교 교무실 만들기 진행

선생님(대개 개발자가 아님)과 함께 그 학교 교직원 사이트를 만든다. 지식은 `kit/docs/`에 있고, 이 스킬은 **순서와 기록**을 맡는다. 대화가 끊기고 다음 세션은 아무것도 기억하지 못하므로, `school-profile.md`(학교 사정)와 `progress.md`(어디까지 했나)가 세션 사이의 유일한 다리다. 이 두 파일을 늘 최신으로 두는 것이 이 스킬의 절반이다.

스크립트는 Node 하나로 돌고(의존성 없음) 저장소 뿌리에서 실행한다:

| 스크립트 | 하는 일 |
|---|---|
| `node .agents/skills/school-office/scripts/plan.mjs <모듈 id …> [--skip id]` | 고른 모듈의 선행 조건을 채워 단계 순서를 짠다. `--list` 로 id 목록 |
| `node .agents/skills/school-office/scripts/memo.mjs <모듈 id …> --stage N --title 이름 --out docs/design/NN-이름.md` | 설계 메모 뼈대 — 그 모듈의 함정 노트 본문과 관문을 옮겨 넣는다. 카탈로그에 없으면 `--new "이름"` |
| `node .agents/skills/school-office/scripts/gate.mjs [--modules id,id]` | 코드만 보고 찾는 자동 관문 + 손으로 확인할 목록. ❌ 가 있으면 종료 코드 1 |

(Claude Code 에서는 같은 스크립트가 `.claude/skills/school-office/scripts/` 에도 있다. 어느 쪽을 불러도 된다.)

## 1. 지금 어디인지 먼저 본다

| 상황 | 할 일 |
|---|---|
| `school-profile.md` 가 없다 | → **2. 시작(인터뷰)** |
| 있는데 `progress.md` 「단계 계획」이 비어 있다 | → **3. 계획** |
| 단계를 진행 중이다 / 「다음 단계」, 「○○ 만들자」 | → **4. 단계 진행** |
| 「관문 검사」, 단계를 끝내려 한다 | → **5. 관문** |
| 「어디까지 했어?」, 「이어받았어」 | → **6. 상태·인수인계** |
| 「키트 업데이트해 줘」, 「새 판 나왔대」 | → **6-1. 키트 업데이트** |

두 파일이 있으면 먼저 읽고, 마지막 위치와 다음 할 일을 선생님께 두세 줄로 말한 뒤 시작한다. 「지난번에 2단계 공지까지 했고, 오늘은 3단계 시간표 차례예요. 시간표 파일을 받아 둔 게 있으면 주세요.」처럼.

## 2. 시작 — 인터뷰

`kit/docs/10-인터뷰.md` 의 다섯 마당을 따른다. 그 문서에 없는 운영 요령만 여기 적는다.

- **들은 즉시 적는다.** `kit/templates/school-profile.md` 를 루트로 복사해 두고, 한 마당이 끝날 때마다 채운다. 인터뷰 도중 대화가 끊겨도 다음 세션이 이어 묻게 하려는 것이다. 모르는 칸은 「모름(나중에)」.
- **한 번에 세 개까지 묻고, 보기를 준다.** 선생님은 「RLS」나 「크론」을 모를 수 있다. 질문은 학교 말로: 「교직원끼리 연락은 주로 무엇으로 하세요? (쿨메신저 / 단체 채팅방 / 기타)」.
- **4마당(불편)은 선생님 말 그대로** 적는다. 나중에 설계 메모 1절로 자동으로 옮겨져, 「왜 이걸 만드는지」를 단계마다 다시 보게 된다.
- **2마당(운영)이 비면 1단계로 가지 않는다.** 관리자 합의·계정 명의·AI 비용 주체는 코드보다 먼저다. 막히면 관리자께 드릴 한 쪽 소개 글을 같이 쓴다.
- 불편을 모듈로 옮길 때는 `kit/docs/02-모듈카탈로그.md` 의 「덜어 주는 불편」과 맞춰 보고, 맞는 모듈을 이름과 한 줄 설명으로 제안한다. 카탈로그에 없는 불편은 「새 모듈 후보」로 적는다.

## 3. 계획

1. 선생님이 고른 모듈을 **급한 순서대로** 넣어 `plan.mjs` 를 돌린다. 핵심 모듈(뼈대·급식·공지·홈·시간표·일정·담임·자료실·알림)은 자동으로 앞에 들어간다. 학교에서 정말 안 쓰는 핵심 모듈만 `--skip`.
2. 결과 표를 `progress.md` 「단계 계획」에 붙이고, **「계획 메모」를 선생님 말로 풀어** 전한다. 자동 추가·순서 조정에는 이유가 적혀 있다 — 「칠판 알림을 하려면 담임 배정과 알림이 먼저 있어야 해서 앞에 넣었어요」.
3. 표 아래에 **선생님 불편(school-profile 4절)이 각각 몇 단계에서 풀리는지** 한 줄씩 적는다 — 선생님이 계획을 자기 문제의 순서로 읽게 하려는 것이다.
4. 「이 순서로 갈까요?」를 묻고, 확인되면 0단계(`kit/docs/00-준비물.md`)부터.

계획은 바뀌어도 된다. 바뀌면 `plan.mjs` 를 다시 돌려 표를 갈아 끼우고, 「결정 기록」에 왜 바꿨는지 한 줄.

## 4. 단계 진행 — 다섯 걸음

한 단계는 늘 같은 다섯 걸음이다. 걸음을 건너뛰고 싶어질 때가 가장 위험하다(특히 3→5로 바로 가기).

**① 설계 메모** — `plan.mjs` 가 출력한 그 단계의 `memo.mjs` 명령에 `--out docs/design/NN-이름.md` 를 붙여 뼈대를 만든다. 그다음 빈칸을 이 학교에 맞게 채운다:
- 2절 화면: 누가, 휴대폰/PC 어디서, 무엇을 누르나.
- 3절 데이터와 권한: 표마다 「누가 읽나·누가 쓰나·얼마나 두나·학생 정보」. 이 표가 곧 RLS 정책이고 RLS 테스트 목록이다. 여기서 정하지 않은 권한은 구현 중에도 만들지 않는다.
- 6절 함정: 이미 옮겨져 있다. 해당 없는 것은 「해당 없음」으로 지운다 — 읽지 않고 넘어가지 않게 하려는 장치다.
- 8절 선생님께 확인할 것: 학교 사정을 모르면 지어내지 말고 여기 적는다.

**② 확인** — 메모를 요약해 보여 주고 「이대로 만들까요?」를 묻는다. 화면과 「누가 볼 수 있나」 위주로 말한다(표 이름·SQL 말고). 선생님이 고친 내용은 메모에 반영하고 상태를 「선생님 확인」으로.

**③ 구현** — 작게 나눠 만든다. 화면 하나가 실제로 돌면 다음으로.
- 1단계는 `kit/docs/04-뼈대설계.md` 와 `05-보안기준선.md` 를 따른다.
- 라이브러리 코드를 쓰기 전에, 설치된 버전의 공식 문서를 확인한다(Next.js·Supabase는 버전마다 규칙이 바뀐다 — 함정 41).
- 새 표를 만들면 같은 커밋에 RLS 테스트를 둔다.
- 학교 값(이름·색·교시·학년 수)은 설정 파일 한 곳에만.

**④ 관문** — 5절.

**⑤ 기록** — `progress.md` 를 고친다(7절 형식). 커밋 메시지에 운영 DB 적용 여부(「운영 DB 적용함 / 미적용」)를 적는다. 마이그레이션을 운영에 적용하는 일은 선생님 허락을 받고 한다.

## 5. 관문

1. `gate.mjs --modules <이번 단계 모듈>` 을 돌린다.
2. **❌ 막힘**은 고친다. 고치기 전에는 다음 단계로 가지 않는다. 비밀 값이 이미 커밋·푸시됐다면 지우는 것만으로는 부족하다 — 기록에 남으므로 그 키를 새로 발급(회전)해야 한다고 선생님께 분명히 말한다.
3. **⚠️ 확인**은 고치거나, 그대로 두는 이유를 `progress.md` 「결정 기록」에 적는다(예: 「lib/weekly/date.ts 의 toISOString 은 날짜 산술용이라 유지」). 이유 없이 넘기지 않는다.
4. **손으로 확인할 것**은 실제로 해 본다. 브라우저 미리보기·테스트 실행은 직접 하고, 실제 휴대폰(특히 아이폰 홈 화면 앱)·대시보드 설정처럼 선생님만 할 수 있는 것은 무엇을 어떻게 볼지 한 줄씩 부탁한다. 확인하지 못한 항목은 「미확인」으로 남긴다 — 통과로 적지 않는다.
5. 설계 메모 7절에 체크하고, `progress.md` 「단계 계획」 표에 관문 통과일을 적는다.

단계 몇 개마다(특히 첫 공개 전) `gate.mjs` 를 모듈 지정 없이 한 번 더 돌리고 `kit/docs/05-보안기준선.md` 를 처음부터 훑는다 — 모듈 사이에서 생기는 빈틈은 단계별 관문으로는 안 보인다.

## 6. 상태·인수인계

- 「어디까지 했어?」: `progress.md` 를 읽고 지금 단계·마지막으로 한 일·다음 할 일·막힌 것을 다섯 줄 안으로. 관문을 못 넘은 단계가 있으면 그것부터 말한다.
- 「운영 이어받았어」: 위 요약 + `progress.md` 「운영 메모」(크론·환경변수 이름·학기마다 할 일)를 설명하고, `kit/docs/08-인수인계.md` 체크리스트를 같이 확인한다. 이어받는 분이 개발자가 아니면, 첫날 할 일로 「작은 글자 하나 고쳐 배포해 보기」를 권한다.

## 6-1. 키트 업데이트

원본 키트의 새 판을 받는다. 자세한 것은 `kit/docs/09-키트업데이트.md`.

1. 커밋하지 않은 변경이 있으면 먼저 커밋한다(되돌릴 지점). 스크립트도 그렇지 않으면 적용을 거부한다.
2. `node kit/scripts/update-kit.mjs` 로 미리 본다. 바뀐 점(CHANGELOG)과 파일별 처리(새로·바뀜·지움·그대로 둠·`.kit-new`)를 선생님 말로 요약해 「적용할까요?」를 묻는다.
3. 허락받으면 `--apply`. 선생님이 고친 키트 파일은 그대로 남고, 양쪽이 다 바뀐 파일만 `파일.kit-new` 가 생긴다.
4. `.kit-new` 마다 두 판을 비교해 선생님이 고친 내용을 살려 합치고 `.kit-new` 를 지운다. 무엇을 살릴지 판단이 갈리면 선생님께 묻는다.
5. `gate.mjs` 를 다시 돌린다(새 판에서 검사 항목이 늘었을 수 있다). 커밋 메시지 「키트 업데이트 A → B」, `progress.md` 결정 기록에 한 줄.

## 7. progress.md 쓰는 법

다음 세션의 에이전트(또는 이어받는 선생님)가 이것만 읽고 이어 갈 수 있게 쓴다. 날짜는 절대 날짜로.

```markdown
## 지금 위치
- 단계: 3 시간과 일정 — ③ 구현 중
- 하던 일: 시간표 변환기. 교사 3명 대조 중 2명 맞음, 「체육」 교실 칸 처리 남음
- 다음에 할 일: 변환기 마무리 → 관문(gate.mjs --modules timetable,calendar,homerooms)

## 결정 기록
- 2026-10-12 — 로그인은 이름+비밀번호(학교 구글 계정이 없는 선생님 6명) — 인터뷰 2마당
- 2026-10-15 — ⚠️ lib/date.ts toISOString 유지: 날짜 더하기 산술용, 「오늘」은 todayInSeoul()
```

## 8. 선생님과 말하는 법

- 쉬운 한국어로. 전문 용어는 처음 나올 때 한 줄로 푼다(「RLS — 표의 줄마다 누가 볼 수 있는지 데이터베이스가 직접 지키는 규칙」).
- **무엇을 만들지는 선생님이, 어떻게는 네가.** 갈림길(예: 로그인 방식, 기존 자료 옮기는 시기)만 묻고, 기술 선택은 기본값으로 진행하며 한 줄로 알린다.
- 끝났다고 말하기 전에 실제로 확인한다. 확인하지 못한 것은 그렇다고 말한다.
- 학교 사정·사람 이름·전화번호를 지어내지 않는다. 모르면 묻거나 빈칸(○○)으로 둔다.
- 보내는 일(교직원 전체 알림)과 지우는 일(운영 데이터)은 하기 전에 무엇이 일어나는지 말하고 허락을 받는다.
