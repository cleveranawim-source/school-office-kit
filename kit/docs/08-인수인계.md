# 인수인계 — 내가 떠나도 사이트가 남도록

교사가 만든 학교 사이트가 가장 자주 무너지는 때는 **만든 사람이 전근 가거나 업무가 바뀔 때**다. 공립학교는 순환 근무가 있어서 몇 년 안에 거의 반드시 온다. 처음부터 아래를 지켜 두면 이어받는 사람이 하루 만에 운영을 시작할 수 있다.

## 처음 만들 때 (0단계에서)

1. **계정 명의를 학교 공용으로.** GitHub·Supabase·Vercel·AI 회사 계정을 학교 공용 메일(예: 정보부 공용 계정)로 만든다. 개인 계정으로 이미 만들었다면, 조직(팀)을 만들어 학교 공용 계정을 소유자로 함께 넣어 둔다.
2. **결제 수단**이 개인 카드라면, 언제 학교 예산으로 옮길지 관리자와 정해 둔다. AI를 선불 충전으로 쓰면 남은 충전금을 누가 보는지도 정한다.
3. **비밀 값 보관 장소**를 정한다. `.env.local`의 값들을 학교가 관리하는 안전한 곳(예: 학교 비밀번호 관리 도구, 봉인한 문서)에 따로 둔다. 대화방·메일에 붙여 넣지 않는다. 구글 열쇠 파일처럼 파일로 받은 열쇠는 저장소 밖에 둔다.

## 문서 구조 — 다음 사람(과 다음 세션의 AI)이 읽을 곳

사이트가 커지면 「왜 이렇게 만들었나」가 코드보다 먼저 사라진다. 원본 학교는 한 달 반 동안 문서를 몇 번 갈아엎은 끝에 아래 모양으로 자리 잡았다. 처음부터 이렇게 나눠 두기를 권한다.

| 파일 | 담는 것 | 담지 않는 것 |
|---|---|---|
| `AGENTS.md` 「우리 학교 규칙」 | 명령 몇 줄, **느슨하게 하지 않는 규칙**만. 규칙마다 정본 파일과 그 규칙을 지키는 테스트 이름 | 기능 설명, 결정의 긴 까닭 |
| `docs/features.md` | 기능별 절. 결정과 동작을 **날짜·결정한 사람·까닭**과 함께 | 고치는 순서 |
| `docs/debugging.md` | 고치기 안내. 이 컴퓨터의 사정(어떤 열쇠가 있고 없는지, 무엇을 직접 못 보는지), 작은 수정 순서, 화면별 코드 위치, 최근 바뀐 것 | 규칙 |
| `PRODUCT.md` | 누가 쓰나, 무엇을 위한 사이트인가, 제품 원칙, 접근성 약속 | 기술 규칙 |
| `docs/design/` | 단계별 설계 메모(`memo.mjs`), 화면 시안 | |
| `docs/specs/`, `docs/plans/` | 큰 기능의 설계서와 구현 계획(날짜를 이름 앞에) | |
| `docs/handoffs/` | 하던 일을 다른 대화·사람에게 넘길 때 지금 상태와 남은 일 | |
| `school-profile.md`, `progress.md` | 학교 사정, 단계 기록·결정 기록·운영 메모(키트 양식) | |

규칙 문서에 적는 한 줄은 이런 모양이다.

```
- 저장소 파일을 시크릿 키로 서명하기 전에 lib/storage-path.ts 의 isSafeObjectPath 로 거른다. tests/unit/storage-path.test.ts
- 새 표에는 「교직원만」 제한 정책도 건다. tests/rls/member-only.test.ts
```

- 규칙에는 **어디가 정본인지**(파일·함수 이름)와 **무엇이 지키는지**(테스트 이름)를 붙인다. 다음 세션의 AI가 그 규칙을 느슨하게 고치려 할 때 테스트가 막는다.
- 기능별 결정에는 날짜와 결정한 사람(이름 대신 역할도 된다)을 붙인다. 「누가 이렇게 하자고 했나」를 모르면 이어받는 사람이 되돌려도 되는지 판단할 수 없다.
- 결정이 바뀌면 옛 줄을 지우고 새 결정을 날짜와 함께 쓴다. 까닭이 중요하면 옛 결정을 한 줄로 남긴다.

### 규칙 문서가 커지면

규칙 문서는 에이전트가 매번 읽는다. 커지면 읽는 비용이 늘고, 중요한 규칙이 설명에 묻힌다. 원본 학교는 규칙 문서가 24KB까지 불었다가 5KB로 줄였다.

1. 규칙 문서에서 「느슨하게 하지 않는 규칙」과 명령만 남긴다.
2. 나머지 기능 설명은 **고치지 말고 그대로** `docs/features.md`의 그 기능 절로 옮긴다(옮기면서 고치면 무엇이 바뀌었는지 모른다).
3. 남긴 규칙마다 「자세한 까닭은 features.md 「○○」 절」을 붙인다.
4. 같은 커밋에서 규칙과 코드가 어긋난 곳을 찾아 고친다(문서와 코드가 다르면 다음 세션은 문서를 믿는다).

## 운영하는 동안

- `progress.md`의 「운영 메모」에 다음을 적어 둔다(값은 빼고 이름과 위치만).
  - 환경변수 이름과 각각 어디서 받았는지(`.env.example`에도 이름을 모두 적는다)
  - 크론 등록 내역(이름, 시각, 부르는 주소, Vercel 크론인지 `pg_cron`인지)
  - 학기마다 할 일(교직원 명단 갱신, 휴직·복직 반영, 시간표 업로드, 담임 배정, 조직표 갱신, 외부 링크 만료 갱신 등)
  - 외부 연동마다 담당자(예: 보건 선생님께 매년 2월 새 공유 링크 받기)
  - AI·Supabase·Vercel 사용량을 언제 누가 보는지
- 관리자 권한을 가진 교사를 **두 명 이상** 둔다.

## 넘길 계정과 열쇠

쓰는 모듈에 따라 아래가 있다. 각각 **누구 명의인지, 이어받는 분이 들어갈 수 있는지**를 확인한다.

| 계정·열쇠 | 넘기는 방법 |
|---|---|
| GitHub 저장소 | 조직 소유자로 추가 |
| Supabase 프로젝트 | 조직 소유자로 추가. 데이터베이스 비밀번호·시크릿 키는 보관 장소에서 |
| Vercel 프로젝트 | 팀 소유자로 추가. 환경변수는 이름 목록과 대조 |
| AI 회사 콘솔 | 조직 소유자로 추가, 결제·충전 담당 바꾸기 |
| 웹푸시 열쇠(VAPID) | 보관 장소에서. 새로 만들면 모든 구독이 끊긴다 |
| 나이스·공공데이터포털 인증키 | 신청한 사람 명의다. 이어받는 분 명의로 새로 받아 바꿔 끼워도 된다 |
| 학교 구글 워크스페이스 전용 계정(공유 드라이브 읽기) | 워크스페이스 관리자가 관리. 넣어 둔 드라이브 목록과 열쇠 다시 받는 방법(`07-AI도우미.md` 10절) |
| 구글 캘린더 주소(ICS) | 관리 화면 설정. 캘린더 소유자가 바뀌면 주소가 바뀔 수 있다 |
| 카카오톡 채널·챗봇 | 채널 관리자 추가. 스킬 비밀 키는 보관 장소에서 |
| 교실 칠판 토큰 | 관리 화면에서 다시 발급할 수 있는지 확인 |

## 넘길 때 체크리스트

- [ ] 이어받는 분을 위 표의 계정·조직에 소유자로 추가했다
- [ ] 비밀 값 보관 장소와 여는 방법을 전달했다
- [ ] `progress.md` 운영 메모와 규칙 문서(`AGENTS.md` 「우리 학교 규칙」)를 함께 읽었다
- [ ] 이어받는 분이 직접 한 번 배포해 봤다(작은 글자 하나 고치기)
- [ ] 이어받는 분이 학기 작업 하나(예: 교직원 추가)를 직접 해 봤다
- [ ] 내 개인 계정을 조직에서 뺐다(넘긴 뒤 한 달쯤 지나서)

## 이어받는 분이 개발자가 아닐 때

이 저장소를 Claude Code나 Codex로 열고 「운영을 이어받았어. 지금 상태를 알려 줘」라고 말하면, 에이전트가 `school-profile.md`·`progress.md`와 규칙 문서를 읽고 설명한다. 오류를 고칠 때는 `docs/debugging.md`부터, 기능을 고칠 때는 `docs/features.md`의 그 절부터 읽게 한다. 그래서 이 파일들을 늘 최신으로 두는 것이 가장 좋은 인수인계다.
